# Importing

Paste a URL and start an import. Core detects the importer from that URL. A WordPress site serves the REST API at `/wp-json`. That importer reads the public pages, the WordPress sitemaps, and the public page and post lists. It does not need a plugin on the WordPress site. Any other site uses the public website crawler. That crawler reads `robots.txt` and `/sitemap.xml` when they exist, and follows links from `/` when they do not. A caller can also pass an explicit list of URLs.

Defaults: 5,000 pages and 20,000 assets, set in Admin under Settings, Importer. Link depth defaults to 6 (`IMPORT_MAX_DEPTH`).

The fidelity report lists missing assets, CSS backgrounds, pages that depend on a plugin (forms, search, calendars, logins, comments), and shared blocks that were left in the page because they were not an exact match. Overview describes each of those blocks in one plain sentence. The technical note stays on the import and is not shown there. Forms that collect a visitor's input are pointed at the site form endpoint and stored as lead forms. Search, login, comment, cart, checkout, payment, file-upload, and third-party forms are noted and left as they were. Contact Form 7 and Gravity Forms are mapped by the WordPress importer. Blocks that match on most pages are stored once under `_inc/` and referenced from the pages. Pages that share a structure become a template under `_templates/`. A site skill is written to `.flagstage/skills/`, and a drift manifest records which pages use each include. When the import finds articles, it also writes `.flagstage/listings.json`. The build turns dated articles into listing pages from that file. Preview and the live site omit those files.

The New site dialog keeps one address field. After the address is entered it shows the detected importer, and the choice can be changed before the import starts. The web process records the site and starts a one-off import task. Locally, with no cluster set, the same import runs in the web process. The site Overview shows the stage, pages found, pages done, and skipped pages while the crawl runs. When the import finishes, and before Go live, Overview lists pages, shared sections, page types, and blocks that stayed on their pages. The import stores the source. Preview and Go live build the public files from it, stitching includes. The first import becomes live only after someone chooses Go live. That first publish is refused when the built pages are missing text, links, images, or pages from the import. A generated listing and a pagination URL that now redirects are not missing. A later publish warns about a removed page or a large loss of text and still goes live. In development, `pnpm dev:sites` serves the published files. Add `{slug}.localhost` to your hosts file and open it on that server's port.

Go live, publishing an edit, and a scheduled publish copy the site's redirects into the CloudFront key value store. A visitor who requests a stored path, including a query string such as `/?p=ID`, gets a 301. Any other request is a published file. A site whose redirects would exceed the store limits does not go live. Those limits are in [Deploy on AWS](self-hosting/aws.md).

Leave the source unset and detection chooses the importer. The public crawler's id is `public`. [Write your own importer](importers.md) to register another one.
